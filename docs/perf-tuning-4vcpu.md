# 4 vCPU 上的性能调优记录（v2 链路）

目标机：`shanghai4c4g`，AMD EPYC 7K62 的 4 vCPU 切片，`sse4_2 avx avx2 fma`（**无 AVX-512 / 无 AVX512-VNNI**），
CPU 后端，无 GPU。本文所有数字都在**串行窗口**里测得，并附测量方法，因为这台机的噪声底线是 **±10%**。

## 0. 先量天花板，再谈优化

`tests/bwpeak.c`（`cc -O3 -mavx2 -mfma -fopenmp`）：

| 线程 | copy | triad | dot（2 读） | FMA 峰值 |
| --- | --- | --- | --- | --- |
| 1 | 21.8 | 24.7 | 22.7 GB/s | 83.9 GFLOPS |
| 2 | 30.9 | 28.4 | 32.0 GB/s | 167.0 GFLOPS |
| 3 | 29.1 | 31.7 | 34.8 GB/s | 248.7 GFLOPS |
| 4 | 30.6 | 33.0 | **37.1 GB/s** | **319.3 GFLOPS** |

带宽在 2–3 线程就饱和，算力线性到 4 线程。**这两个数就是后面所有"还差多少"的分母**：
算力受限的阶段按 319 GFLOPS 算，带宽受限的阶段按 37.1 GB/s 算。

## 2. 做完的优化与实测收益

| 优化 | 机制 | 收益 | 验证方式 |
| --- | --- | --- | --- |
| **AR：删掉每 token 的 KV cache 全量 concat** | 每层把 `cache[0..L)` 复制到新缓冲再让 flash 读回 = 39 MB/token 纯拷贝（2.02 ms，占解码 33%）。改为新列 cpy 到常驻 cache 第 `len` 列、flash 读视图 | 流量 145 → 106 MB/token，带宽利用 63% → **73%**；解码 13.7 → **7.5 ms/token** | **179 步 token 概率转储 md5 前后一致**（逐位相同），`bench_ar` 7.07 → 4.41 ms/token |
| **dec：ConvTranspose 相位分组子像素** | 原来按 `M=d_hi-d_lo+1` 均匀取 tap，实际每相位只有 `K/s` 个非零 → 白算 1.875×/1.5×/1.25×；且 stage0 每次调用刷 15.7 MB 权重（只有 17% 峰值）。按相位分组合并、bias 折进尾、`dlo<0` 用 `ggml_pad` 表达 | dec MAC 85.00 → 83.78 GMAC，stage0 权重 15.7 MB → 2–3 MB；synth 1822 → **1706 ms** | 串行 A/B 3 次中位数；对拍 `wav cos 0.999917` 不变 |
| **蒸馏 HuBERT 前端** | 2.97M 参数学生模型替代教师 | 参考侧 1584 → **289 ms（5.4×）**；48× 实时 | 对同一段音频 vs torch fp32：`max_abs 1.0e-05, corr 1.000000000` |
| **g2ps 文本前端（默认）** | 纯 numpy，替代 ONNX G2PW | **2.92 ms/句、0.283 ms/字**，且不再需要 608 MB 的 `g2pW.onnx` | 9 句 930 字计时 + 多音字正确性（银行/行踪/重量级/重新） |

**合并后（`f7a5204`）全链：4261 → 3050 ms，RTF 0.535 → 0.383（−29%）**，其中 synth 1762 ms（RTF 0.221）。

## 4. 试过但否决的方案（负结果，都带数字）

| 方案 | 结果 | 判据 |
| --- | --- | --- |
| **im2col + GGML GEMM 替代直接卷积** | resblock 形状（K=11/3, IC=OC=128, T=16480）直接卷积**快 1.87× / 2.45×**，且 im2col 要 88.5 MB 中间缓冲 | 直接卷积本来就是 62% 峰值，im2col 的额外搬运让它更差；唯一胜场（ups0，OC=2560、T=206）恰好被相位分组从另一侧解决 |
| **手写 AVX2 ResBlock1 内核**（`GSV_V2_DEC=kernels`） | synth 1706 → **3030 ms（慢 1.8×）**；~60–70 GFLOPS = 19–22% 峰值 | 内核级 vs 朴素参考 `maxdiff = 0`、线程 1/2/3/5/7 逐位相同、对 torch 仍 `cos 0.999917`——**正确但不够快**。保留在分支 `agent/nzq20e/dec-opt-76x` 作记录 |
| **resblock 跨块求和"按位融合"** | wav cos 掉到 **−0.0037** | `res` 槽位装的是**块内**残差（`x = x + conv2(conv1(x))` 串 3 次），硬塞跨块和会破坏语义；被 parity 对拍当场抓住并回退 |
| **Q8_0 权重用于 dec conv** | 未实施 | AVX2 无 VNNI，需把激活也量化到 Q8_1（误差主源），预期 1.3–1.6×，与"手写内核"失败的原因同源（dec 是算力受限而非带宽受限），优先级已下调 |

## 5. 还没动的天花板

- **dec 的 80.7 GMAC（95% 算力）已经 62% 峰值**，纯 fp32 下的空间是 0.49 s→1.0 s 区间的地板（398 帧 = 161.9 GMAC = 323.8 GFLOP → **1015 ms 地板**）。想再快只能换数值格式（int8，需 VNNI 才有意义）或换机器。
- **AR prefill 410 ms 占 AR 的 30%**，56 GFLOP / 137 GFLOPS = 43% 峰值，卡在 llama.cpp 的 q8_0 GEMM 内核里（q4k 的 prefill 只快 13.6% → 不是带宽问题）。这条要改 `patches/`，不在 `gsv_ar.cpp` 内。
- **RTF 理论下限**（dec 满峰值 + AR 满带宽 + 其它忽略）：0.162（dec）+ 0.06 ≈ **0.22 左右**，即当前 0.383 距离"4 核实测极限"还有约 1.7× 空间，全部集中在 dec 的算力效率与 AR prefill 的 GEMM 内核。

## 6. 测量方法（重要）

这台机被多个进程共享过，出现过 **load 13.3 / 同一命令测出 38032 ms（正常 2500 ms）**的情况。因此
`scripts/bench_serial.sh` 设了三道闸：

1. 启动前与两次运行之间检查"是否有进程 >20% CPU"，有则拒绝启动；
2. 两个二进制严格串行，绝不并发；
3. 每次运行用 `/usr/bin/time -f %P` 读**该 job 实际拿到的 CPU%**，4 线程满跑应为 380–400%，
   低于阈值（默认 370，共享 VM 上 365–370 属正常 steal）的样本**直接丢弃**，不参与中位数。

低于 **5%** 的差异在这台机上不可测，不要据此下结论。
